kanna-di は、コンテナ構造体のコンストラクタを生成します。各フィールドの値は、フィールドの型と同じパッケージか、コンテナと同じパッケージにある関数（プロバイダ）と、それらがさらに必要とするプロバイダを、普通の Go のコードとして順に呼び出して得られます。

[kanna](https://go-kanna.github.io/ja/) コードジェネレータファミリーの 1 つです。Go 1.26 以上が必要です。実行時に import するものはありません。生成コードが呼び出すのは、自分で書いた関数だけです。

## インストール

```sh
go get -tool github.com/go-kanna/di/cmd/kanna-di
```

## 使い方

層に分かれたアプリケーションを考えます。ドメインがリポジトリとメール送信者を宣言し、ユースケースがそれらに依存し、インフラストラクチャがそれらを実装し、ハンドラがユースケースを呼び出します。各層は、コンストラクタを型と同じパッケージに置きます:

```go
// package user, the domain
type Repository interface {
	Save(ctx context.Context, u User) error
	Find(ctx context.Context, id ID) (User, error)
}

// package mail, the domain
type Sender interface {
	Send(ctx context.Context, m Message) error
}

// package usecase
func NewRegisterUser(repo user.Repository, mailer mail.Sender) *RegisterUser
func NewGetUser(repo user.Repository) *GetUser

// package postgres, the infrastructure
func NewUserRepository(db *sql.DB) *UserRepository

// package sendgrid, an external API
func NewSender(cfg config.Config) *Sender

// package handler
func NewUser(registerUser *usecase.RegisterUser, getUser *usecase.GetUser) *User

// package config
func Load() (Config, error)
```

コンポジションルートには、プログラムを構成するものを保持する構造体がすでにあります。ハンドラとルーティングを持つサーバです。これに `//kanna:container` を付けます。コンポジションルートでしか決められないことは、その構造体のそばに書きます。ドメインの各インターフェースにどの実装を使うかと、標準ライブラリが提供するものの開き方です。

```go
package main

import (
	"database/sql"
	"net/http"

	"example.com/shop/internal/config"
	"example.com/shop/internal/handler"
	_ "example.com/shop/internal/infra/postgres"
	_ "example.com/shop/internal/infra/sendgrid"
	"example.com/shop/internal/mail"
	"example.com/shop/internal/user"
)

//go:generate go tool kanna-di

// server serves the shop's HTTP API.
//
//kanna:container
type server struct {
	_ user.Repository `di:"with=postgres.NewUserRepository"`
	_ mail.Sender     `di:"with=sendgrid.NewSender"`

	users *handler.User
}

func (s *server) routes() http.Handler {
	mux := http.NewServeMux()
	mux.HandleFunc("POST /users", s.users.Register)
	mux.HandleFunc("GET /users/{id}", s.users.Get)
	return mux
}

func openDB(cfg config.Config) (*sql.DB, func(), error) {
	db, err := sql.Open("pgx", cfg.DSN)
	if err != nil {
		return nil, nil, err
	}
	return db, func() { db.Close() }, nil
}
```

`go generate ./...` を実行すると、コンテナと同じディレクトリに `di_gen.go` が書き出されます:

```go
// Code generated by kanna-di. DO NOT EDIT.

package main

import (
	"slices"

	"example.com/shop/internal/config"
	"example.com/shop/internal/handler"
	"example.com/shop/internal/infra/postgres"
	"example.com/shop/internal/infra/sendgrid"
	"example.com/shop/internal/usecase"
)

// newServer initializes dependencies and constructs server.
func newServer() (*server, func(), error) {
	cfg, err := config.Load()
	if err != nil {
		return nil, nil, err
	}
	var cleanups []func()
	cleanupAll := func() {
		for _, c := range slices.Backward(cleanups) {
			c()
		}
	}
	db, cleanup, err := openDB(cfg)
	if err != nil {
		return nil, nil, err
	}
	if cleanup != nil {
		cleanups = append(cleanups, cleanup)
	}
	repo := postgres.NewUserRepository(db)
	mailer := sendgrid.NewSender(cfg)
	registerUser := usecase.NewRegisterUser(repo, mailer)
	getUser := usecase.NewGetUser(repo)
	users := handler.NewUser(registerUser, getUser)

	return &server{
		users: users,
	}, cleanupAll, nil
}
```

```go
func main() {
	s, cleanup, err := newServer()
	if err != nil {
		log.Fatal(err)
	}
	defer cleanup()

	log.Print(http.ListenAndServe(":8080", s.routes()))
}
```

`*usecase.RegisterUser` は、型と同じパッケージにある関数 `usecase.NewRegisterUser` から得られます。`*sql.DB` は、コンテナと同じパッケージにある `openDB` から得られます。ドメインのインターフェースである `user.Repository` と `mail.Sender` は、コンテナが指定した実装から得られます。`config.Config` は一度だけ読み込まれ、`openDB` と `sendgrid.NewSender` で共有されます。登録するものはありません。コンストラクタのパラメータが変わると、次の `go generate` がそれを呼び出すコードを変更します。

kanna の生成器を 2 つ以上使うなら、必要な順に動かす [`go tool kanna gen`](https://github.com/go-kanna/kanna) で動かしてください。

## プロバイダ

プロバイダは、最初の戻り値がパッケージで宣言された型（構造体、インターフェース、その他の名前付き型）またはそのポインタであるトップレベル関数です:

| 戻り値 | コンストラクタ |
|---|---|
| `T` | |
| `T, error` | エラーも返す。プロバイダのエラーをそのまま渡す |
| `T, func()` | クリーンアップも返す。[クリーンアップ](#クリーンアップ)を参照 |
| `T, func(), error` | その両方 |

可変長パラメータ `...T` には、コンテナが `T` の出どころを言っているときだけ、その値を渡します。出どころとは、引数（`di:"arg"`）、選んだプロバイダ（`di:"with=..."`）、埋め込んだもの、フィールドのない構造体の型ならその型のフィールドです。それ以外は何も渡さず、関数も探しません。呼び出しが何を受け取るかを、コンテナから読み取れるようにするためです（[プロバイダの選択](#プロバイダの選択)を参照）。プロバイダはコンストラクタごとに 1 回呼び出され、その戻り値を必要とするものはすべてそれを共有します。`string`、`int`、`[]byte` のように型に名前のない値は、型では配りません。型だけでは、DSN とアドレスのように、どの値が何を表すのかを区別できないからです。そのような型を返す関数はプロバイダにならず、`di:"arg"`、`with=`、コンテナが埋め込んだ構造体のフィールドからも配られません。このような値には `type DSN string` のように独自の型を与えてください。`NewDeps` に対する `MustNewDeps` のように、ラップされる関数と同じパッケージにある must 版は選ばれず、その関数が使われます。panic ではなくエラーがコンストラクタに届くようにするためです。ジェネリックな関数も、型引数を選ぶものがないので、プロバイダになりません。ほかにその型を返すものがなければ、エラーがその関数を挙げて理由を示します。

kanna-di は必要な型ごとに、次の順に探して最初に見つかったものを使います:

1. コンストラクタの引数（`di:"arg"`）
2. コンテナがその型に選んだプロバイダ（`di:"with=..."`）
3. コンテナが埋め込んでいるもの: 埋め込んだ、または `_` として宣言した構造体の公開フィールド、もしくはその場で組み立てるコンテナの `with=`（[コンテナ](#コンテナ)を参照）
4. フィールドのない構造体の型（そのポインタは含まない）なら、ゼロ値。それがその型の持つ唯一の値で、作るのに関数は要らないので、コンテナのフィールドと同じく `newTicker(Clock{})` のように渡します（[コンテナ](#コンテナ)を参照）
5. コンテナのパッケージにある関数（公開か非公開かは問わない）と、その型を宣言するパッケージが自分のモジュール（コンテナの上の go.mod のモジュール）にあれば、そのパッケージの公開関数。2 つのパッケージの関数は合わせて数えるので、片方にある関数がもう片方の関数を隠すことはありません

コンテナが埋め込んでいるものは、どの関数よりも先に使われます。埋め込みは、コンテナが何を持つかの宣言だからです。そのため、埋め込んだ構造体にフィールドを足すと、それ以降は、その型を作っていた関数に代わって、そのフィールドの値が使われます。

go.work があっても、自分のモジュールの範囲は広がりません。CI によくある、go.work のないチェックアウトでも、同じものが見つかるようにするためです。go.work が含むほかのモジュールの関数は、ほかのどのモジュールの関数とも同じく、`with=` で選びます。

どれも見つからなければ生成を止めます。同じレベルで 2 つ見つかった場合も同じです。エラーは、必要になった経緯をフィールドまでさかのぼって示します:

```console
$ go generate

  via server.users → handler.NewUser → usecase.NewRegisterUser
  return one from a function in package main, take it with di:"arg", or choose a provider with di:"with=..."
./server.go:11:2: error: 2 functions in package usecase return *usecase.GetUser
  usecase.NewGetUser (../../internal/usecase/get_user.go:12:6)
  usecase.NewCachedGetUser (../../internal/usecase/get_user.go:30:6)
  via server.users → handler.NewUser
  choose one with _ *usecase.GetUser `di:"with=usecase.NewGetUser"`

  usecase.NewRegisterUser (../../internal/usecase/register_user.go:14:6)
  mail.NewWelcome (../../internal/mail/welcome.go:9:6)

```

それ以外の場所にある関数は、コンテナが指定した場合にのみ使われます。testutil パッケージのヘルパーや、同じ型を返すフィクスチャがあっても、コンテナが受け取るものは何も変わりません。標準ライブラリや他のモジュールも探しません。io の関数のうち `io.Writer` を返すのは `MultiWriter` だけで、これは引数なしで呼び出すとどこにも書き込みません。このような型には、コンテナと同じパッケージに関数を書くか、`with=` で選んでください。`sql.Open` に DSN が必要なように、ほとんどはいずれにせよ設定が必要です。

## プロバイダの選択

`di:"with=<ref>"` は、フィールドの型のプロバイダをコンテナ全体に対して選びます:

| `<ref>` | 指すもの |
|---|---|
| `NewUserRepository` | コンテナのパッケージにある関数 |
| `postgres.NewUserRepository` | コンテナのファイルが postgres として import しているパッケージの関数。Go がコードを読むのと同じ |

Go は使っていない名前つきの import を拒むので、`with=` でしか使わないパッケージは `_` で import します。そのパッケージは、上の `postgres` と `sendgrid` のように、パッケージ自身の名前で呼びます。ほかは探さないので、ファイルが import していないパッケージはエラーになり、エラーには何を import すればよいかが示されます。

プロバイダの戻り値は、その型に代入可能でありさえすれば構いません。インターフェースに実装を与えられるのはこのためです。名前付きフィールドでは、`with=` は値も格納します。`_` では選ぶだけで、構造体の場合はそのフィールドがコンテナに値を提供します（[コンテナ](#コンテナ)を参照）。

可変長パラメータも、`with=` で選んだものを受け取ります。kanna-orm が生成する repository は、時計を `NewOrder(db DBTX, opts ...option.Option)` のようにオプションで受け取ります。コンテナでオプションを選べば、組み立てるすべての repository に渡り、どの時計を使うかが組み立てる場所で見えます:

```go
func clockOption() option.Option { return option.WithClock(appClock{}) }

//kanna:container
type server struct {
	_ option.Option `di:"with=clockOption"`

	users *handler.User
}
```

```go
	opts := clockOption()
	orders := postgres.NewOrder(db, opts)
```

コンテナは 1 つの型の値を 1 つだけ持つので、複数のオプションは `option.Join(option.WithClock(appClock{}), option.WithHook(audit{}))` のように 1 つに束ねて渡します。1 つの repository にだけ別のオプションを渡したいときは、コンテナの隣にその repository のコンストラクタを書いて選びます。コンテナのオプションも、そのコンストラクタの可変長パラメータに渡ります:

```go
func newOrders(db postgres.DBTX, opts ...option.Option) postgres.Order {
	return postgres.NewOrder(db, append(opts, option.WithHook(audit{}))...)
}

//kanna:container
type server struct {
	_ option.Option  `di:"with=clockOption"`
	_ postgres.Order `di:"with=newOrders"`

	users *handler.User
}
```

コンテナは 1 つの型の値を 1 つだけ作り、それを必要とするすべてに渡します。そのため、同じ型の 2 つのフィールドに別々のプロバイダを選んだり、2 つのパラメータとして受け取ったりはできません。primary と replica の 2 つの `*sql.DB` のように分けたいときは、`type ReplicaDB struct{ *sql.DB }` のように型を分け、それを返すプロバイダを書きます。

```console
./server.go:9:2: error: package postgres has no function NewUserRepositry (field _)
  did you mean NewUserRepository?
./server.go:9:2: error: postgres.NewOrderRepository returns *postgres.OrderRepository, which does not implement user.Repository (missing method Find) (field _)
```

## コンテナ

`//kanna:container` を付けた構造体は、タグで別の指定をしない限り、すべてのフィールドが解決されます:

| フィールド | 名前付き | `_` |
|---|---|---|
| タグなし | フィールドの型を解決し、値を格納する | 公開フィールドを持つ構造体なら解決するが、何も格納しない。それ以外はエラー |
| `di:"with=<ref>"` | ref で解決する。ref はコンテナ全体でその型に使われる | その型に ref を選ぶ。何も格納しない |
| `di:"arg"` | フィールドの名前のパラメータとして受け取り、格納する | 型にちなんだ名前のパラメータとして受け取るだけ |
| `di:"arg=<name>"` | 同上。パラメータ名を明示する | 同上。パラメータ名を明示する |
| `di:"-"` | フィールドには何もしない | エラー |

タグのない名前付きフィールドや埋め込みフィールドのうち、型がフィールドのない構造体であるもの（そのポインタは含まない）は、ゼロ値のままになります。ゼロ値がその型の持つ唯一の値だからです。`todov1.UnimplementedTodoServiceServer` を埋め込む gRPC サーバに、そのためのプロバイダは必要ありません。

フィールドや型にちなんだ名前のパラメータは、import に名前を譲ります。手で書くコードと同じく、import はパッケージの名前を保ちます。フィールド `config config.Config` なら `config2 config.Config` で、`di:"arg=cfg"` と書けば `cfg` になります。`_` の `context.Context` は、Go のコードでの呼び方どおり `ctx` です。明示した名前は保たれ、生成ファイルがその名前で必要とするインポートのほうがリネームされます。明示した名前が、パッケージのトップレベルで宣言されている名前や、Go があらかじめ宣言している名前である場合はエラーです。

コンテナが受け取る、または選んでいるのに、何にも必要とされていないものには警告が出ます:

```console
./server.go:12:2: warning: nothing in server needs the context.Context it takes with di:"arg"
./server.go:9:2: warning: nothing in server needs user.Repository, so its with= chooses nothing
```

埋め込まれた構造体やそのポインタは、他のフィールドと同じように解決され（`di:"arg"` を付けた場合はパラメータとして受け取られ）、格納されます。その公開フィールドは、昇格したものも含めて、コンテナの他の部分に値を提供します。ただし、その構造体自体を組み立てるために必要なものには使えません。Go が浅いフィールドで同じ名前の深いフィールドを隠すように、浅いフィールドは同じ型の深いフィールドを隠します。同じ深さに 2 つある場合は、その型が必要になったときにエラーになります。

```go
//kanna:container
type App struct {
	infra.Deps `di:"arg"` // its DB and Cache serve the providers of Users

	Users *handler.User
}
```

`_` フィールドの構造体やそのポインタも、同じようにコンテナに値を提供しますが、格納はされません。そのためコンテナは、その構造体も、埋め込みなら昇格するはずのフィールドやメソッドも持ちません。解決されるのは、その構造体かそのフィールドのいずれかが必要になったときです。タグがなければ他のフィールドと同じように解決され、`di:"arg"` や `with=` があれば、それによって受け取られるか選ばれます。ユースケースは、インフラストラクチャがまとめたものをこの方法で利用します:

```go
//kanna:container
type DeleteTodo struct {
	_ *infra.Deps // infra.NewDeps provides it; its Transactor and Todos fill the fields below

	transactor tx.Transactor
	todos      repository.Todo
}
```

```go
func NewDeleteTodo() (*DeleteTodo, func(), error) {
	var cleanups []func()
	cleanupAll := func() {
		for _, c := range slices.Backward(cleanups) {
			c()
		}
	}
	deps, cleanup, err := infra.NewDeps()
	if err != nil {
		return nil, nil, err
	}
	if cleanup != nil {
		cleanups = append(cleanups, cleanup)
	}
	transactor := deps.Transactor
	todos := deps.Todos

	return &DeleteTodo{
		transactor: transactor,
		todos:      todos,
	}, cleanupAll, nil
}
```

同じパッケージのコンテナ（それ自体に `//kanna:container` が付いた構造体）をタグなしで埋め込むと、そのコンテナは自身のコンストラクタではなく、このコンストラクタの一部として、ここでフィールドごとに組み立てられます。そのコンテナが引数として受け取るものは、このコンストラクタも受け取ります。ただし、このコンテナ自身がその型を受け取るか、`with=` で選ぶか、その型のフィールドを持つ構造体を埋め込んでいる場合は、そちらが使われ、その引数は受け取りません。外側のコンテナが言ったことが、その場で組み立てるコンテナが受け取るものより優先されます。そのコンテナの `with=` は、このコンテナ自身の `with=` の次に、このコンテナで使われます。組み立てた値は、フィールドをどこに宣言したかによらず、その型を必要とするこのコンテナのほかのものにも使われます。テストがサーバを書き直さずに、一部のプロバイダを差し替えて組み立てられるのは、この仕組みによるものです（[テスト](#テスト)を参照）。別のパッケージのコンテナは、非公開フィールドをここから設定できないので、代わりにそのコンストラクタで組み立てられます。コンテナ型の名前付きフィールドも同様です。別のパッケージのコンテナが値を非公開フィールドに持ち、このコンテナもその型の値を必要とするときは、生成時にエラーになります。このコンストラクタが 2 つ目の値を作ることになるからです。1 つの値を共有するには、そのコンテナで値を公開フィールドに持つか、`di:"arg"` で受け取るようにして、このコンストラクタから渡します。2 つの値を使い分けるなら、それぞれに専用の型を与えます。

コンストラクタの名前は構造体の名前で決まります。`Server` なら `NewServer`、`server` なら `newServer` で、構造体が公開されているときだけ公開されます。設定を先に読み込むなど、別の名前の関数が要るときは、それを手で書いて、生成したコンストラクタを呼びます。

コンストラクタの引数は、それを受け取るフィールドの順に並び、その場で組み立てるコンテナの引数は、自分のものの後ろに、そのコンテナのフィールドの順で続きます。`context.Context` が先頭に来るのは、先頭に宣言したときだけです。Go の慣習どおり `ctx` を先頭にしたいときは、外側のコンテナでほかより先に受け取ります。外側で受け取れば、その場で組み立てるコンテナはもう受け取りません。

```go
//kanna:container
type base struct {
	_   context.Context `di:"arg"`
	dsn DSN             `di:"arg"`
}

//kanna:container
type server struct {
	_ context.Context `di:"arg"` // without it, newServer(src source.Source, ctx context.Context, dsn DSN)
	base

	_ source.Source `di:"arg=src"`

	users *handler.User
}
```

```go
func newServer(ctx context.Context, src source.Source, dsn DSN) (*server, func(), error)
```

ディレクティブにはオプションを指定できます:

| ディレクティブ | 効果 |
|---|---|
| `//kanna:container returns=<type>` | コンストラクタが返すものを宣言する: 値で返すなら構造体、またはそれが実装するインターフェース（デフォルトはポインタ） |
| `//kanna:container must` | エラーを返す代わりに panic する `MustNewServer`（`newServer` に対しては `mustNewServer`）も生成する |

must 版は、失敗するプロバイダがなくても、コンストラクタを呼ぶだけの関数として書かれます。失敗するプロバイダが増えても減っても、must 版を呼ぶコードを変えずに済むようにするためです。

ジェネリックな構造体はコンテナにできません。コンストラクタに型引数を選ぶ手段がないからです。`di` タグがあるのにディレクティブがない構造体には警告が出ます。ディレクティブのスペルミスと、空行で構造体から離れていて、その doc コメントになっていないディレクティブも同様です。構造体の型でないもの（`type Level string`、型の別名、インターフェース、関数など）に付けたディレクティブはエラーです。

ディレクティブは、コメントマーカーに密着させて書いてください。Go が `//kanna:…` をディレクティブとして扱うのは、この 2 つが隣接している場合のみです。スペースを入れると、`// kanna:container` は doc コメントの一部のままになり、`go doc` や pkg.go.dev に表示されます。kanna-di もこの形式をディレクティブとして扱わず、期待する書き方を指摘します。

## クリーンアップ

何かを開くプロバイダは閉じ方を返し、コンストラクタはそれらすべてをまとめた 1 つのクリーンアップを返します:

```go
func newServer() (*server, func(), error) {
	// ...
	var cleanups []func()
	cleanupAll := func() {
		for _, c := range slices.Backward(cleanups) {
			c()
		}
	}
	db, cleanup, err := openDB(cfg)
	if err != nil {
		return nil, nil, err
	}
	if cleanup != nil {
		cleanups = append(cleanups, cleanup)
	}
	cache, cleanup, err := openCache(cfg)
	if err != nil {
		cleanupAll()
		return nil, nil, err
	}
	if cleanup != nil {
		cleanups = append(cleanups, cleanup)
	}
	// ...

	return &server{
		// ...
	}, cleanupAll, nil
}
```

クリーンアップは、プロバイダが実行された順序の逆順に実行されます。プロバイダが失敗すると、それより前に実行されたプロバイダのクリーンアップを実行してから、エラーを返します。must 版もクリーンアップを返します。閉じるものがないプロバイダは、クリーンアップに nil を返してもかまいません。nil のクリーンアップは呼ばれず、コンストラクタが返すクリーンアップが nil になることもありません。コンストラクタが引数として受け取るものや、埋め込んだ、または `_` として宣言した構造体の中に見つけたものは呼び出し側のものであり、決して閉じられません。`io.Closer` を実装しているという理由で閉じられるものもありません。

## テスト

`_test.go` ファイルで宣言されたコンテナも生成の対象で、同じディレクトリの `di_gen_test.go` に、そのファイルが宣言するパッケージ（パッケージ自体、またはその外部 `_test` パッケージ）のコードとして生成されます。次のコンテナはパッケージ自体にあり、サーバを埋め込んでいるので、サーバそのものです。ただし、リポジトリと送信者を `with=` で選ぶ代わりに引数として受け取って、ここで組み立てられます。すると `*sql.DB` も `config.Config` も必要なくなるので、`openDB` と `config.Load` は呼び出されず、`newTestServer` はクリーンアップもエラーも返しません。

```go
//kanna:container
type testServer struct {
	*server

	_ user.Repository `di:"arg"`
	_ mail.Sender     `di:"arg"`
}

func TestRegisterUser(t *testing.T) {
	s := newTestServer(memory.NewUserRepository(), &fakeSender{})
	srv := httptest.NewServer(s.routes())
	defer srv.Close()
	// ...
}
```

テスト用コンテナが受け取るものや選ぶものは、サーバが選ぶものだけでなく、受け取るものにも代わります。サーバが送信者を `di:"arg"` で受け取っていたとしても、ここに `` _ mail.Sender `di:"with=newFakeSender"` `` と書けば `newFakeSender` が呼び出され、`newTestServer` は送信者を受け取りません。

このテストは、初回の実行で `newTestServer` が書き出される前からそれを呼び出しています。kanna-di は、読み込んだパッケージを、これから書き出す内容を組み込んだ状態でもう一度型チェックします。そのため、まだ存在しないコンストラクタや、これから受け取るものや返すものが変わるコンストラクタの呼び出しがあっても止まりません。その時点で間違っているものは報告され、何も書き出されません。これから書き出すコンストラクタと合わない呼び出しや、コンストラクタがないために隠れていた間違い（コンストラクタが返すものにないメソッドなど）です。

テスト用コンテナのパッケージの関数には、その `_test.go` ファイルの関数も含まれます。`_test.go` ファイルで宣言されたプロバイダは、そのパッケージのテストにのみコンパイルされるので、そのパッケージのテスト（パッケージ内と外部の両方）のコンテナにだけ値を提供します。1 つのディレクトリでは、2 つのテストパッケージのどちらか一方にしかテスト用コンテナを置けません。両方に置くと `di_gen_test.go` を共有することになるからです。

## kanna-config の設定

[kanna-config](https://github.com/go-kanna/config) は、設定の構造体 `X` の隣に `LoadX(src source.Source) (X, error)` を書きます。これは型の隣にある関数なので、`X` のプロバイダになります。設定をまとめるコンテナは、ソースを引数として受け取ります。型から名前を付けると `source` の import に譲って `source2` になるので、名前を明示します:

```go
//kanna:container returns=Config
type Config struct {
	_ source.Source `di:"arg=src"`

	API      config.API
	Database config.Database
}
```

```go
func NewConfig(src source.Source) (Config, error) {
	api, err := config.LoadAPI(src)
	if err != nil {
		return Config{}, err
	}
	database, err := config.LoadDatabase(src)
	if err != nil {
		return Config{}, err
	}

	return Config{
		API:      api,
		Database: database,
	}, nil
}
```

設定が要るコンテナは、`` _ Config `di:"arg=cfg"` `` のようにそれを受け取ります。そのフィールドがプロバイダに使われるので、`config.Database` がデータベースを開く関数に届きます。

ほかのプロバイダと同じく、コンストラクタは最初に失敗した `LoadX` の誤りを返し、その後の `LoadX` は呼びません。`API_PORT` と `DATABASE_WRITER_URL` の両方が誤っていても、報告されるのは `API_PORT` だけです。誤った設定をまとめて報告したいときは、コンテナの代わりに関数を手で書き、それぞれの `LoadX` を呼んで誤りをつなげます:

```go
func NewConfig(src source.Source) (Config, error) {
	api, errAPI := config.LoadAPI(src)
	database, errDatabase := config.LoadDatabase(src)
	if err := errors.Join(errAPI, errDatabase); err != nil {
		return Config{}, err
	}
	return Config{API: api, Database: database}, nil
}
```

## wire、fx、dig から移る

[wire](https://github.com/google/wire) もコードを生成し、プロバイダの形も同じです。プロバイダは `T`、`T, error`、`T, func()`、`T, func(), error` を返し、コンストラクタは injector と同じく、誤りと 1 つのクリーンアップを返します。違うのは、配線をどこで言うかです:

| wire | kanna-di |
|---|---|
| `wire.Build` を呼ぶ injector 関数 | `//kanna:container` を付けた構造体。ディレクティブは構造体に付けるもので、関数に付けるとエラーになる |
| `wire.Build`、`wire.NewSet`、プロバイダセット | なし。プロバイダは型で、コンテナの隣か型の隣から探す（[プロバイダ](#プロバイダ)を参照） |
| injector の引数 | `di:"arg"` |
| `wire.Bind(new(I), new(*T))` | `` _ I `di:"with=NewT"` `` |
| `wire.FieldsOf(new(*Deps), "DB")` | `Deps` を埋め込むか `_ *Deps` と宣言する。その公開フィールドがコンテナに使われる |
| `wire.Value`、`wire.InterfaceValue` | コンテナの隣に、その値を返す関数を書く |
| 同じ型の 2 つの値（2 つの `string` など） | wire と同じく、それぞれに型を与える。ただし `string`、`int`、`[]byte` はそもそも型では配らない |

可変長パラメータ `...T` には、コンテナが出どころを言っているときだけ値を渡し、関数は探しません（[プロバイダ](#プロバイダ)を参照）。

[fx](https://github.com/uber-go/fx) と [dig](https://github.com/uber-go/dig) は、実行時にコンストラクタを登録し、リフレクションで呼ぶので、足りないものは実行時に報告されます。kanna-di は生成時に報告し、書き出すのはコンストラクタを呼ぶ素の Go で、実行時に import するものはありません。dig の `name:"…"` のように名前で区別する値は、ここでは型を分けます。ライフサイクルのフックはありません。サーバはコンストラクタが返したあとに `main` が起動し、プロバイダが開いたものはクリーンアップが閉じます。

## フラグ

```sh
kanna-di [flags] [packages]
```

| フラグ | 意味 |
|---|---|
| `-tags <list>` | カンマ区切りのビルドタグ |
| `-check` | 書き出す代わりに、出力が最新であることを検証する。不要な出力が残っていないことも含む。`KANNA_CHECK=1` でも同じ |
| `-v` | 書き出した、削除した、変更しなかったファイルを一覧表示する |
| `-deps` | 実行が読み書きするものを、`kanna` コマンドのために JSON で表示して終了する |
| `-version` | バージョンを表示する |

引数のパッケージは、コンテナのある場所を示すもので、プロバイダの取得元を示すものではありません。デフォルトはカレントディレクトリのパッケージなので、`//go:generate go tool kanna-di` に引数は不要です。成功した実行は、警告以外何も出力しません。すべての構造体から `//kanna:container` がなくなったパッケージの `di_gen.go` と `di_gen_test.go` は、実行時に読み込んだパッケージのコードがそのコンストラクタをまだ呼び出していない限り、削除されます。どちらの名前でも、生成コードのヘッダがないファイルには決して触れません。削除する `go generate` は `open ...: no such file or directory` で終わります。これは go generate 自身のエラーで、ジェネレータを実行する前にパッケージのファイルを列挙しているためです。ファイルは意図どおり削除されています（[golang/go#36068](https://github.com/golang/go/issues/36068)）。

## サンプル

[`example`](example) は、上で述べた層（ドメイン、ユースケース、インフラストラクチャ、ハンドラ）からなる小さなショップの依存関係を組み立てます。プロバイダは、インターフェースへのバインド、引数、埋め込みコンテナから見つけます。クリーンアップ、must 版、リポジトリをメモリ上のものに差し替えるテスト用コンテナも使っています。CI はこれを再生成し、出力が変わる場合は失敗します。
